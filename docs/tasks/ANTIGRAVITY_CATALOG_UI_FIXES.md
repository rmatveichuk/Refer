# Gemini: исправить три воспроизведённые ошибки каталогов

Продолжи реализацию ANTIGRAVITY_CATALOG_UI_IMPLEMENTATION.md. Codex независимо запустил проектный `.venv/Scripts/python.exe -m unittest discover -s tests`: все 104 теста проходят. Однако три пропущенных случая воспроизведены на временных данных. Исправь код и добавь регрессионные проверки в рамках первоначального задания.

Воспроизведение: `research/search_audit/verify_catalog_handoff.py`; результаты `research/search_audit/catalog_handoff_review.json`. Все три поля ошибок равны true. Скрипт фиксирует ошибки прежнего кода; после исправления адаптируй его к проверке правильного поведения либо оставь с явной исторической пометкой.

## 1. Отмена не отменяет изменения групп

CatalogDialog получает общий SourceGroupStore из MainWindow. Создание, переименование, перемещение и удаление групп вызывают немедленный save; перенос источника изменяет общую память даже без записи. После «Отмена» файл/память уже изменены, дерево главного окна может оставаться старым.

Нужен изолированный черновик для ВСЕХ операций организации, порядка и включения источников/групп. «Применить» атомарно сохраняет единый снимок и обновляет общий store только после успеха. «Отмена», Escape, крестик отбрасывают черновик. Не записывать промежуточные изменения в рабочий файл с последующим откатом. Запуск импорта/сканирования с несохранённым черновиком должен применять изменения явно и согласованно, не терять их молча.

## 2. Удаление с переносом в потомка создаёт цикл

Создать Parent → Child, вызвать delete_group(Parent, target_group_id=Child): Child получает parent_id равный своему id. Обходы могут зависнуть. UI исключает при выборе цели только удаляемую группу, но не потомков.

Запретить в store перенос содержимого в удаляемую группу или любого её потомка до изменения состояния; исключить эти цели в UI. Проверить ребёнка и глубокого потомка, неизменность памяти/файла при отказе, безопасный перенос в соседнюю группу и корень. При загрузке JSON проверять ссылки/циклы и сообщать ошибку вместо зависания или молчаливого сброса данных.

## 3. Ошибка записи оставляет изменённую память

При OSError в os.replace файл сохраняет старые байты, но create_group уже добавил группу в память. Аналогично остальные сохраняющие методы мутируют состояние до save. Следующее успешное сохранение может неожиданно записать правку, ранее объявленную неуспешной. Текущий тест проверяет только файл.

Сделать публичные сохраняющие операции транзакционными: при ошибке опубликованная память и файл остаются прежними, последующая запись не возвращает отвергнутые изменения. Черновик диалога можно оставить для повторной попытки, не публикуя в общий store.

Qt-обработчики создания, переименования и удаления ловят только ValueError, а save выбрасывает RuntimeError. Обработать ошибки записи понятным сообщением без необработанного исключения, закрытия приложения и ложного успеха. При ошибке «Применить» сохранить черновик в открытом окне для повторной попытки.

## Проверки и передача

Проверить на временных данных память, файл и повторное открытие диалога после отмены/применения/ошибки записи. Сохранить существующие проверки фильтрации, скрытия, дерева и сканирования. Использовать проектный .venv, рабочую SQLite/FAISS не менять, не переиндексировать и не собирать EXE. Коммиты не делать.

Обновить CATALOG_UI_IMPLEMENTATION_REPORT.md и RESUME.md с фактическим результатом и количеством тестов. После исправления ручная проверка: создать/переименовать/переместить группу → «Отмена» → открыть снова (старое состояние); повторить с «Применить» (новое); отключить/включить ветку (выдача и источники согласованы); пересканировать папку и открыть веб-импорт из каталогов.
